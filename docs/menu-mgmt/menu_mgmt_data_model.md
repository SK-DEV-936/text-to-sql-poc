# Menu Management: Detailed SQL Data Model

To support the migration from n8n to the custom Python Core Engine, we recommend the following schema design. This ensures **merchant isolation**, **versioning**, and **auditability** for all mutations.

---

## 1. Physical Schema Design (MySQL)

```sql
-- ============================================================
-- 1. MERCHANTS (Multi-tenant Root)
-- ============================================================
CREATE TABLE `merchants` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `business_name` VARCHAR(255) NOT NULL,
  `api_key` VARCHAR(64) UNIQUE NOT NULL, -- Used for AI Agent auth
  `status` ENUM('active', 'suspended') DEFAULT 'active',
  `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ============================================================
-- 2. MENUS (A Merchant can have multiple menus: Dine-in, Catering, etc.)
-- ============================================================
CREATE TABLE `menus` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `merchant_id` INT NOT NULL,
  `title` VARCHAR(255) NOT NULL, -- e.g., 'Main Lunch Menu'
  `description` TEXT,
  `is_active` TINYINT(1) DEFAULT 1,
  `version` INT DEFAULT 1,
  PRIMARY KEY (`id`),
  FOREIGN KEY (`merchant_id`) REFERENCES `merchants`(`id`) ON DELETE CASCADE,
  INDEX `idx_merchant_menu` (`merchant_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ============================================================
-- 3. CATEGORIES (Menu Sections)
-- ============================================================
CREATE TABLE `categories` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `menu_id` INT NOT NULL,
  `name` VARCHAR(100) NOT NULL, -- e.g., 'Appetizers'
  `rank` INT DEFAULT 0, -- For UI sorting
  PRIMARY KEY (`id`),
  FOREIGN KEY (`menu_id`) REFERENCES `menus`(`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- ============================================================
-- 4. MENU ITEMS (The core data for mutations)
-- ============================================================
CREATE TABLE `menu_items` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `merchant_id` INT NOT NULL, -- Direct FK for strict security audit
  `category_id` INT NOT NULL,
  `name` VARCHAR(255) NOT NULL,
  `description` TEXT,
  `price` DECIMAL(10, 2) NOT NULL,
  `image_url` VARCHAR(512),
  `is_available` TINYINT(1) DEFAULT 1,
  `metadata` JSON, -- Optional (Calories, Allergens)
  `updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  FOREIGN KEY (`merchant_id`) REFERENCES `merchants`(`id`),
  FOREIGN KEY (`category_id`) REFERENCES `categories`(`id`) ON DELETE CASCADE,
  INDEX `idx_security_merchant` (`merchant_id`),
  INDEX `idx_item_search` (`name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

---

## 2. Security Design Principles

### 2.1 The "Audit-First" Approach
Every mutation generated by the `MenuMutationAgent` must target `menu_items`. The **Security Auditor Agent** will verify that:
1.  The `INSERT` statement includes `merchant_id`.
2.  The `UPDATE` statement’s `WHERE` clause explicitly contains `merchant_id`.

### 2.2 Handling Multimodal Extractions
When `MenuVisionAgent` extracts a new price for "Classic Burger":
*   The **Conflict Resolver Agent** will query `menu_items` filtering by `merchant_id` and a fuzzy name match.
*   If a match exists, it generates an `UPDATE`.
*   If no match exists, it generates an `INSERT` into the specific `category_id`.

## 3. Human-in-the-Loop (Staging)
We recommend a "Staging" table for proposed mutations to facilitate the HITL approval flow before the core database is touched.

```sql
CREATE TABLE `pending_mutations` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `merchant_id` INT NOT NULL,
  `proposed_sql` TEXT NOT NULL,
  `status` ENUM('pending', 'approved', 'rejected') DEFAULT 'pending',
  `ai_confidence` DECIMAL(3,2),
  `original_image_ref` VARCHAR(255), -- Reference to S3 bucket
  `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB;
```
